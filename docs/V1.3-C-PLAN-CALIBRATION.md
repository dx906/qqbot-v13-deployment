## 1. C-1 领先度：实测反向，不可用

### 标定方法
7 条正例（问题有明确事实答案）+ 6 条噪声（与人格库无关），各取 k=8，计算 `lead = relevance[0] − relevance[1]`。全部走 8127 真库、`reinforce=false`（不写回）。

### 实测数据

|---|---|---:|---:|---:|---:|

| 正例 | 我在哪个学校读书 | 0.0055 | 0.3571 | 0.3516 | 1.8893 |
| 正例 | 你给自己起的名字是什么 | **−0.0273** | 0.4691 | 0.4964 | 2.4819 |

### 分布对比

| | min | median | max |
|---|---:|---:|---:|
| 正例 lead | −0.0273 | **0.0216** | 0.2151 |
| 噪声 lead | 0.0449 | **0.0895** | 0.1543 |

**噪声的 lead 中位数（0.0895）高于正例中位数（0.0216）。判据方向是反的。**

### 阈值扫描

| lead_min | 正例通过 | 噪声误通过 |
|---|---:|---:|
| 0.00 | 6/7 | 6/6 |
| 0.02 | 4/7 | 6/6 |
| 0.03 | 3/7 | 6/6 |
| 0.05 | 2/7 | 5/6 |
| 0.08 | 2/7 | 3/6 |
| 0.10 | 1/7 | 3/6 |
| 0.15 | 1/7 | 1/6 |

**没有任何阈值能把正例和噪声分开**：提高阈值先杀正例。

### 为什么失败
文档假设「真答案甩开第二名、噪声命中挤成一团」。但本库只有 122 条、全部围绕同一个人，**同一个人身上的相邻事实彼此高度相关**——问到猫时「鲸宝名字」「鲸汐档案」的 relevance 紧贴「煤球」；而噪声 query（如「写快速排序」）反而可能只命中一条泛泛的条目、第二名掉得远，lead 反而更大。

即：**lead 度量的是「第二名掉得多远」，在这个小库里它与「这条是否真答案」不相关。**

### 结论
- 代码保留（`compute_leads` + `classify(lead_min=)`），默认 `RECALL_LEAD_MIN=0.0`（关闭）
- 该判据只在「库大、主题分散」时才可能有效；本库不适用，**不要开启**
- 交付文档口径：《大肥鱼系统》§3「确定性优先 ≥0.55 且领先 ≥0.15」这一条**经实测证伪**，是本文档评审中唯一被数据推翻的建议

## 2. C-2 protected 豁免：实测有效

### 语义
当 `protected=true` 且某条命中满足：
- `tier == 0`（身份锚点）**或** `identity >= 0.85`（元数据身份强度）
- 且 `relevance >= 0.35`（确实相关）
- 且 `score >= weak_min`（够格进注入，新增地板）

→ 强制归 `strong`，绕过 `strong_min`/`strong_rel_min` 的绝对分门槛。

### 实测（query「我的猫叫什么名字」，V1.2 两档参数）

| 配置 | strong | weak | protected | 被豁免的条目 |
|---|---:|---:|---:|---|
| `protected=false` | 1 | 2 | 0 | — |
| `protected=true` | **3** | 2 | **3** | id15 煤球(tier0)、id9 鲸宝名字(tier0)、id41 鲸汐(tier0) |

三条被豁免的全是真身份锚点，无误伤。单测另覆盖：rel 不足不豁免、identity 不足不豁免、score 低于 weak_min 不豁免（15/15 PASS）。

### 结论
- 能力已验证，但**默认关**（`PROTECTED_ENABLED=False`），以保证「不传键 = V1.2 行为」
- V1.3 插件侧当前不传 `protected`，因此线上暂未启用
- 开启方式（三选一）：请求体带 `protected: true`；或改 `config.py` 的 `PROTECTED_ENABLED`；或插件侧传参
- 建议先观察一段时间再决定是否默认开，理由是它会让低分身份锚点也进上下文，宁可少注入

## 3. C-3 cohit 共激活边：写入已开，重排保持关

### 表结构
```sql
create table if not exists cohit(
  a_id integer not null,      -- 小 id 在前，保证 (a,b) 唯一
  b_id integer not null,
  n    integer not null default 1,
  last_at real not null,
  primary key (a_id, b_id)
);
create index if not exists idx_cohit_b on cohit(b_id);
```

### 行为
- **写入**（`COHIT_ENABLED=True`）：每次召回把**真正注入**的条目两两连边（dropped 不连），`n += 1`
- **重排**（`COHIT_REWEIGHT=False`，默认关）：锚点 top3 与候选的共激活次数 → `score += 0.03 × log1p(n)`，然后重排
- 写入/重排都有 try/except 包裹，**失败不影响召回**

### 实测
| 场景 | 注入条数 | cohit_pairs |
|---|---:|---:|
| 不带两档参数（k=8 全注入） | 8 | 28 = C(8,2) |
| V1.2 两档参数 | 3 | 3 = C(3,2) |
| protected=true | 5 | 10 = C(5,2) |

单测 12/12 PASS（对称性、n 递增、自反不计、单条无边、C(4,2)=6、去重行数）。

### 为什么重排默认关
冷启动阶段边数少且偏（早期注入组合会自我强化），先只**攒数据**不**用数据**。等有几千条边、能用离线回放验证收益后再开。
